# Подключаемый libman

Каталог содержит экспортируемую версию Sprinter libman 1.3 для DLL форматов
L0 и L1. Она ищет DLL рядом с EXE, ограничивает длину формируемого пути и
освобождает файл, временные страницы, запись таблицы и WIN3 на всех ветках
ошибки.

Для переноса копируется каталог целиком. `libman_core13.asm` является
внутренней реализацией; проекты подключают `libman.asm` либо пару
`libman_core.inc`/`libman_state.inc`.

## Обычное подключение

Если весь менеджер находится в постоянно видимой памяти и не попадает в окно,
выбранное для DLL, достаточно совместимого монолитного include:

```asm
        include "../../libman/libman.asm"

        ld      hl,dll_name
        ld      a,3
        call    LIBMAN.l_load
        jr      c,load_error
        ld      (dll_handle),hl

dll_name:       db "AFNT640.DLL",0
dll_handle:     dw 0
```

`libman13.asm` оставлен как совместимое имя для старых проектов.
Глобальные имена `l_load`, `l_call`, `l_info`, `l_free` также сохранены как
алиасы API; их можно отключить через `LIBMAN_NO_LEGACY_API`.

## Размещение загрузчика в WIN0

Для архитектуры, использующей WIN0 под собственные нужды (с трамплинами в страницу DSS), менеджер может подключаться двумя частями. Загрузчик можно
положить в WIN0, а код вызова DLL, таблицу и изменяемое состояние — в
постоянно отображаемый WIN1:

```asm
        DEFINE  LIBMAN_WIN0
        DEFINE  LIBMAN_MAX_LIBS 8
        DEFINE  LIBMAN_APP_DIR EXE_DIR
        DEFINE  LIBMAN_PATH_CAPACITY 272

        ; WIN0
        include "../../libman/libman_core.inc"

        ; Постоянно отображаемый WIN1
        include "../../libman/libman_state.inc"

EXE_DIR:        db "C:\\SPRED\\",0
```

Порядок include обязателен: сначала `libman_core.inc`, затем
`libman_state.inc`. Части могут находиться в разных исходных файлах/ORG, но
должны собираться в одном пространстве символов.

При `LIBMAN_WIN0` окно 1 зарезервировано за программой: `l_load` принимает
только `A=2` или `A=3`, а для `A=1` возвращает
`LIBMAN.LR_WINDOW`. Это необходимо, потому что `l_call`, `l_free` и
`l_info` исполняются из WIN1 и не могут переключить страницу с собственным
кодом и стеком.

Тестовая раскладка для SprEd даёт следующие размеры:

- `libman_core.inc` в WIN0: 971 байт;
- `libman_state.inc` при `LIBMAN_MAX_LIBS=8`: 644 байта;
- пример строки каталога: ещё 10 байт.

Итого сам менеджер занимает 1615 байт, а вместе с примером каталога —
1625 байт. В показанной раскладке после core до границы WIN0 остаётся
149 байт. Монолитная конфигурация по умолчанию (`LIBMAN_MAX_LIBS=64`)
занимает 1834 байта. Исторический libman 1.3 занимает 1312 байт: цена поиска
рядом с EXE, безопасного unwind и исправлений DSS составляет 522 байта.
До чистки текущий вариант занимал 2344 байта.

Для приложений с небольшой таблицей монолитный вариант при
`LIBMAN_MAX_LIBS=8` занимает 1610 байт; дополнительное отключение поиска
рядом с EXE (`LIBMAN_NO_EXE_DIR`) уменьшает его до 1544 байт.

`LIBMAN_DIAGNOSTICS` добавляет 147 байт подробной диагностики этапов.
Тестовая опция `LIBMAN_CALL_TRACE` добавляет ещё 102 байта и не предназначена
для релизной сборки. Размер проверяется сборочным тестом.

## Поиск DLL

Простое имя 8.3 сначала проверяется как `<каталог EXE>\<имя>`, затем —
относительно текущего каталога. Путь с `\`, `/` или `:` считается явным.
Составной путь строится во временной странице по адресу `C000h`, уже
выделенной загрузчиком. Поэтому постоянный 272-байтовый буфер больше не нужен.
Перед `DSS OPEN` и составной, и исходный путь копируются в этот буфер с
проверкой `LIBMAN_PATH_CAPACITY`. Поэтому исходная строка может находиться в
WIN0; слишком длинный путь отклоняется до `OPEN`.

Исходная строка не может находиться в WIN3: временная страница подключается
туда до чтения имени. По сравнению с первой split-версией экспортируемого
include это breaking-ограничение размещения данных; исторический API вызова
и формат DLL не меняются.

По умолчанию каталог EXE запрашивается через DSS `APPINFO` (`47h`, подфункция
1). Если приложение убирает PSP из адресного пространства, каталог следует
сохранить при старте в постоянно видимой памяти и передать как
`LIBMAN_APP_DIR`, как в примере выше. В split-конфигурации
`LIBMAN_APP_DIR` должен находиться в постоянно видимом WIN1, не в
переключаемом WIN3.

Доступны настройки:

- `LIBMAN_MAX_LIBS` — число записей таблицы, от 1 до 64; по умолчанию 64;
- `LIBMAN_PATH_CAPACITY` — размер буфера пути; по умолчанию 272;
- `LIBMAN_PATH_BUFFER` — необязательный внешний буфер вместо временного
  `C000h`; нужен только для нестандартной интеграции;
- `LIBMAN_APP_DIR` — заранее сохранённая ASCIIZ-строка каталога EXE;
- `LIBMAN_NO_EXE_DIR` — полностью отключить поиск рядом с EXE;
- `LIBMAN_DIAGNOSTICS` — включить этапы загрузки и отдельный статус DLL INIT;
- `LIBMAN_NO_LEGACY_API` — не экспортировать старые глобальные имена `l_*`.

Если используется непосредственный `APPINFO`, ёмкость пути должна быть не
меньше 270 байт. С `LIBMAN_APP_DIR` допустим меньший буфер, но он должен
вмещать фактический каталог, разделитель, имя и NUL.

## API и диагностика

- `LIBMAN.l_load`: `HL` — ASCIIZ-путь, `A` — окно; результат `HL=handle`;
- `LIBMAN.l_call`: `HL` — handle, `B` — номер функции;
- `LIBMAN.l_info`: `HL` — handle, `DE` — стабильный буфер 32 байта;
- `LIBMAN.l_free`: `HL` — handle.

При успешном `l_load` менеджер вызывает entry 0 (`INIT`) до закрытия DLL-файла.
В `A` передаётся DSS-handle этого открытого файла. Менеджер читает и
распаковывает только prefix длиной из поля заголовка `02h`; последующие
физические байты файла остаются trailing payload, а файловый указатель перед
`INIT` установлен на его первом байте. Payload не входит в checksum и может
увеличивать физический DLL-файл сверх 65535 байт. `INIT` должна дочитать
нужные данные до возврата: сразу после неё менеджер закрывает handle. Размер
prefix должен быть от 16 байт до 16 KiB и не больше физического размера файла.
Для сжатого prefix загрузчик дополнительно проверяет, что распаковка не выходит
за WIN3 и заканчивается точно на размере, заданном полями кода и релокаций.

`l_call` подключает страницу DLL через явные DSS-вызовы `SETWIN1/2/3`
(`#39..#3B`). Общий `SETWIN #38` не используется: текущий Estex-DSS неверно
вычисляет slot-port для WIN1, но при этом может вернуть CF=0. Регистры `IX/IY`
сохраняются вокруг DSS-вызова и передаются библиотечной функции без изменений.
Входной CF не влияет на поиск handle.

Сохранена legacy-семантика результата: CF библиотечной функции
распространяется через `l_call` только для функции 0 (`INIT`). Для функций с
номером 1 и выше CF очищается; CF=1 от самого `l_call` по-прежнему обозначает
ошибку диспетчеризации/DSS. Полноценный ABI возврата флагов запланирован
отдельным совместимым API в `TODO.md`.

При ошибке установлен CF, а `LIBMAN.l_reason` содержит:

- `LIBMAN.LR_OPEN` — путь не найден или файл не удалось открыть;
- `LIBMAN.LR_LOAD` — ошибка чтения, формата, памяти, relocation или `init`;
- `LIBMAN.LR_WINDOW` — недопустимое окно.

В компактной сборке всегда доступны `l_reason` и исходный DSS-статус в
`l_dss_error`. При `DEFINE LIBMAN_DIAGNOSTICS` дополнительно активируются:

- `LIBMAN.l_load_stage` — этап загрузки;
- `LIBMAN.l_init_status` — исходный `A`, только если DLL `INIT` вернула CF.

Без `LIBMAN_DIAGNOSTICS` два последних символа совместимости указывают на
общий нулевой байт. Ошибки best-effort cleanup не заменяют уже сохранённую
первичную причину. Значения `l_load_stage`:

| Константа | Значение | Этап |
|---|---:|---|
| `LS_NONE` | 0 | ошибки нет или неверное окно вызова |
| `LS_TEMP_ALLOC` | 1 | выделение временных страниц |
| `LS_TEMP_MAP` | 2 | mapping временной страницы в WIN3 |
| `LS_OPEN` | 3 | открытие DLL, включая предварительную проверку пути |
| `LS_IO` | 4 | seek/read заголовка или файла |
| `LS_FORMAT` | 5 | проверка размера и формата L0/L1 |
| `LS_COPY` | 6 | распаковка, relocation или копирование |
| `LS_TARGET` | 7 | выделение/mapping целевой страницы |
| `LS_INIT` | 8 | вызов DLL `INIT` |
| `LS_CLEANUP` | 9 | закрытие файла или освобождение временного блока |

Например, `LR_LOAD + LS_INIT + l_init_status!=0` означает отказ самой DLL,
а `LR_LOAD + LS_INIT + l_dss_error!=0` — ошибку DSS при mapping перед вызовом
`INIT`. Для внутренних ошибок формата/таблицы оба raw-поля остаются нулевыми.
`A` публичных функций остаётся совместимым с libman 1.3.

Критическое ограничение теперь относится не ко всему include, а к его
runtime-части: `libman_state.inc`, таблица, стек и пользовательские буферы
должны оставаться отображёнными во время `l_load/l_call/l_free/l_info`.
`libman_core.inc` разрешено размещать в WIN0; WIN3 менеджер использует как
рабочее окно и восстанавливает перед возвратом.
